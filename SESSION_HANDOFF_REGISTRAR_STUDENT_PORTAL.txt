PURPOSE
=======
This file documents the work completed in this session for the finals demo. The scope is limited to the Registrar, Student Portal, and the unified JSON datastore. Finance, Faculty, Guidance, Library, Testing, and unrelated departments were not migrated or rewritten.

CANONICAL DATASTORE
===================
The active demo datastore is the root project file:

    campus_system_unified_data_schema.json

The duplicate file below is retained as a legacy snapshot and must not be used for runtime reads or writes:

    Departments/StudentPortal/StudentPortalMain/campus_system_unified_data_schema.json

Both applications use the shared resolver in:

    Shared/CampusSystem.Data/Json/CanonicalJsonStore.cs

The resolver finds the repository root by locating the directory containing Departments and the root JSON file. It does not depend on the current working directory or a machine-specific absolute path. The Registrar UI displays a portable label instead of showing a device-specific path.

The shared store provides:

- Canonical root-file resolution.
- Locked JSON reads and writes.
- Atomic temporary-file replacement for writes.
- JSON parse and write errors that can be surfaced to the calling workflow.
- Collection helpers for unified_seed_data arrays.

IMPORTANT JSON COLLECTIONS
==========================
The Registrar workflow uses these collections in unified_seed_data:

- users
- student_profiles
- enrollments
- fee_assessments
- student_payments
- document_credentials
- certificate_of_registrations

For a newly created student, search by student ID or email in users. Then use the user's numeric id to find related records in the other collections.

REGISTRAR WORKFLOW
==================
The workflow is integrated into the actual Registrar Student Records page. There is no separate DemoRegistrar route.

Main route:

    /StudentRecords

Local demo URL:

    http://localhost:5201/StudentRecords

The workflow supports:

1. Create a pending applicant from the main Student Records page.
2. Generate a random temporary password.
3. Store only a BCrypt password hash in users.password_hash.
4. Store the applicant profile in student_profiles.
5. Create a pending_payment enrollment record.
6. Create a minimum demo fee assessment.
7. Create the required document checklist.
8. Reject duplicate student ID numbers and email addresses.
9. Reject registration before payment.
10. Record a required demo downpayment of PHP 10,000.
11. Prevent duplicate paid payment records for the same student.
12. Activate the account only after payment.
13. Register the student after payment.
14. Create a certificate_of_registrations record after registration.
15. Display the temporary password once after creation so it can be handed to the student for the demo.

The main Registrar model is:

    Departments/Registrar/RegistrarMain/Pages/StudentRecords.cshtml.cs

The main Registrar view is:

    Departments/Registrar/RegistrarMain/Pages/StudentRecords.cshtml

The Registrar application registers CanonicalJsonStore in:

    Departments/Registrar/RegistrarMain/Program.cs

The existing SQL-based Registrar pages and workflows remain in place outside this focused demo path.

PAYMENT RULE
============
The existing seed JSON already contained a PHP 10,000 downpayment for the original sample student. The new Registrar workflow uses PHP 10,000 as the minimum demo payment requirement.

The payment flow is:

    pending applicant
        -> pending_payment
        -> paid / account_created
        -> registered
        -> demo COR created

An unpaid applicant must not receive an active account or a valid demo COR.

PASSWORD SECURITY
=================
New student accounts use:

- A random temporary password generated by the Registrar workflow.
- BCrypt password hashing.
- password_hash in the canonical JSON datastore.

Plaintext password fields were removed from the root canonical JSON file. The Student Portal copy did not contain plaintext password fields.

Do not use password123, NULipa-2026, a student ID as a password, or any other shared default for new accounts.

STUDENT PORTAL AUTHENTICATION
=============================
Student Portal authentication is implemented in:

    Departments/StudentPortal/StudentPortalMain/Services/StudentPortalDbService.cs

The Portal registers the shared JSON store in:

    Departments/StudentPortal/StudentPortalMain/Program.cs

The Portal login page is:

    Departments/StudentPortal/StudentPortalMain/Pages/Login.cshtml
    Departments/StudentPortal/StudentPortalMain/Pages/Login.cshtml.cs

Students may log in with their student ID number or university email and the temporary password supplied by Registrar after payment activates the account.

Authentication behavior:

- Reads users from the canonical root JSON datastore.
- Verifies BCrypt password hashes.
- Requires the account status to be active.
- Creates an ASP.NET session after successful login.
- Redirects unauthenticated users to Login.
- Clears the session on logout.
- Does not fall back to another student if a session ID is invalid.

The Portal enrollment/COR display was updated in:

    Departments/StudentPortal/StudentPortalMain/Pages/Enrollment.cshtml
    Departments/StudentPortal/StudentPortalMain/Pages/Enrollment.cshtml.cs

Unpaid or unregistered students do not receive a validated COR display. The COR is explicitly described as a demo document, not official legal or financial documentation.

HOW TO TEST THE DEMO
====================
1. Start Registrar from the repository root:

       dotnet run --project .\Departments\Registrar\RegistrarMain\RegistrarMain.csproj --no-build --urls http://localhost:5201

2. Open:

       http://localhost:5201/StudentRecords

3. Create a new applicant using a unique email. Leave the student ID blank to generate one, or enter a unique ID.

4. Save the temporary password shown after creation.

5. Verify the new entry in the root JSON file under unified_seed_data.users.

6. Verify related entries under student_profiles, enrollments, fee_assessments, and document_credentials.

7. Try Register before payment. It should fail.

8. Record the PHP 10,000 payment.

9. Verify the account changes from pending to active/account_created and that a student_payments record exists.

10. Register the student and verify that a certificate_of_registrations record is created.

11. Start Student Portal in another terminal:

       Push-Location .\Departments\StudentPortal\StudentPortalMain
       dotnet run --no-build --urls http://localhost:5202
       Pop-Location

12. Open:

       http://localhost:5202/Login

13. Log in using the new student ID or email and the temporary password.

14. Verify the Portal dashboard and enrollment pages show only the authenticated student's data.

15. Test Logout, then revisit a protected page. It should redirect to Login.

KNOWN LIMITATIONS
=================
- This is a local, single-user, demo-only JSON datastore. It is not production-ready.
- Existing SQL-heavy Registrar pages remain SQL-dependent.
- Other campus departments remain outside this change.
- The Registrar demo path is the main StudentRecords route; unrelated Student Records detail and maintenance actions may still use MySQL.
- The existing Student Portal service still contains SQL fallback paths for some non-authentication features. The focused demo authentication and canonical JSON path use the root JSON datastore.
- The demo applicant currently receives a minimum assessment and document checklist. Course/subject selection is limited compared with the full SQL enrollment workflow.
- The temporary password is displayed only in the Registrar response after account creation. It is not stored in plaintext in JSON.
- If Windows Application Control blocks a built shared assembly, the applications may need to be run from an approved location or unblocked by the machine administrator.
